Overview

When the Stakes Are High, the Design Has to Hold

EduTrend is a K-12 classroom behavior tracking platform built for a complex ecosystem of schools, staff, and students. Teachers log incidents in real time. Behaviorists analyze patterns across classrooms. Admins provision organizations and control who sees what. Every piece of data is sensitive. Every permission decision carries real consequences for children.

As Lead Designer, I joined the founding team to build the product from zero. That meant creating the brand identity, the design system, the information architecture, the wireframes, and the high-fidelity mockups for every role-specific surface across web and mobile before a single line of frontend code was written.

The design challenge was not just making something that looked clean. It was building a system where the right person could only ever see exactly what they were supposed to see, and where every interaction felt fast enough for a paraprofessional logging a behavior incident with one hand during a classroom moment.

The Challenge

Five Roles. One Platform. Zero Room for Error.

K-12 behavioral data is legally protected, emotionally charged, and operationally complex. Designing for this environment required understanding not just what each user needed to do, but what they should never be able to see or access by mistake.

Multi-Tenant Architecture

Each school organization required fully isolated data. No behavioral records could ever cross organizational boundaries. The UX had to reinforce this invisible but critical boundary at every decision point.

Permission Complexity

Five distinct roles with different read, write, and analytics permissions. A paraprofessional and a behaviorist might view the same student but through completely different lenses with completely different actions available.

Speed Under Pressure

Paraprofessionals needed to log behavioral incidents in seconds, often in mid-classroom situations. The form design had to be fast, forgiving, and mobile-first without sacrificing the data quality analysts needed downstream.

Safety-Critical Data

Student profiles included allergies, medical information, and behavioral history. Data visibility rules were not a feature to be designed in later. They had to be the foundation everything else was built on top of.

Zero Existing Foundation

There was no design system, no brand, no component library. Everything had to be created from scratch in a way that would scale as the engineering team grew and new surfaces were added post-MVP.

Cross-Platform Parity

The platform needed to work equally well on a teacher's desktop browser and a paraprofessional's phone. The same shared component system had to serve both without compromise on either surface.

Identity and Access Design

Designing for Five Distinct Mental Models

Before designing a single screen, I mapped out every role, their primary goal, their access level, and the actions they would take daily. This role architecture became the structural foundation for every navigation decision, every data display choice, and every permission boundary in the system.

Admin
Full System Access
Provisions organizations, manages users and roles, assigns classrooms, controls permissions across the institution.
Behaviorist
Org-Wide Read Access
Views all behavioral data across the organization. Identifies patterns, generates insights, supports teachers with evidence-based strategies.
Teacher
Classroom-Scoped Access
Logs and monitors behavior for assigned classroom students only. Coordinates with paraprofessionals and reviews behavioral summaries.
Paraprofessional
Assignment-Scoped Access
Logs behavioral incidents quickly and accurately for directly assigned students. Speed and simplicity are the primary UX requirements.
The permission model was not a feature layer on top of the UX. It was the architecture the UX was built inside. Every navigation item, every data table, every action button had to respect role boundaries without ever making the user feel restricted.

Brand and Design System

A System Built to Scale With the Product

EduTrend had no visual language when I joined. I built the brand and design system simultaneously, making decisions that would hold up across an expanding feature set and a growing engineering team. Every token, every component, every pattern was documented for handoff.

Color System

Semantic tokens with full dark mode support

Primary blue anchors trust and action. Semantic success, warning, and error colors carry consistent meaning across every surface. All combinations meet WCAG 4.5:1 contrast ratios.

Component Library

Atomic design from tokens up

35+

Components built from atoms to organisms. Buttons with five variants and all interactive states. Input fields with eight validation states. Form controls, badges, avatars, search, data tables, and navigation all documented and handed off to engineering.

100%

Accessibility was not an audit at the end. Every component was built with contrast ratios, keyboard navigation, screen reader labels, and touch target sizes baked in at the atom level so nothing downstream could accidentally break compliance.

Organization Onboarding

Trust Starts Before the First Login

EduTrend uses an organization-first onboarding model. Before a single teacher or paraprofessional can access the platform, the institution itself is provisioned, verified, and contractually activated. This flow was one of the most complex design challenges in the product because it had to balance institutional formality with digital simplicity.

A school administrator setting up their district for the first time is making a high-stakes decision. The onboarding flow had to feel secure and deliberate without feeling bureaucratic and slow. Every step had to earn trust.

Wireframes for the full organization onboarding journey: institution details, contract review and signing, document approval, payment processing, and confirmation

High fidelity onboarding flow: admin dashboard, organization form, contract review and signing, document upload and approval, payment processing with multiple methods, and organization confirmed state

Identity and Member Management

Provisioning People With the Right Access From Day One

Once an organization is provisioned, admins need to onboard their staff, assign them roles, and scope their access to specific classrooms. The member management surface was designed to make this feel effortless for a school administrator who is not a technical user.

The add member flow surfaces role selection, classroom assignment, and permission scoping in a single focused modal. Role descriptions are written in plain language, not system terminology. Admins can see exactly what a teacher will and will not have access to before confirming the invite.

Every invite generates a role-scoped link so new users land in the right experience the moment they authenticate for the first time.

Member management: staff roster view and role-scoped invite modal

Student Data Design

The Same Student, Seen Differently By Every Role

One of the most nuanced design problems in EduTrend was that multiple roles could access a student record but needed to see and do fundamentally different things. A behaviorist sees behavioral pattern analytics. A teacher sees classroom context and logs recent incidents. A paraprofessional sees a quick-access log form. The same underlying data had to be surfaced appropriately for each context.

Strategic Vision

Designing Beyond the MVP: Three Expansion Models

The K-12 MVP was the starting point, not the ceiling. Working alongside the founding team, I mapped out three distinct platform expansion paths that would take EduTrend beyond the classroom. Each model introduced new user types, new permission hierarchies, and new design challenges. This work shaped how the core architecture was built so that expansion would not require starting over.

Designing the MVP with expansion in mind is not scope creep. It is systems thinking. Every architectural decision I made was evaluated against where the product needed to go, not just where it was.
Core Users

Admin, Behaviorist, Teacher, Paraprofessional

Primary Use Case

K-12 behavior logging, analytics, and organization management

Key Design Challenge

Role-scoped access with classroom-level permission boundaries

New User Types

Clinic Admin, BCBA Supervisor, RBT Therapist, Physician

Expansion Context

Applied behavior analysis clinics and therapeutic organizations with clinical-grade data requirements

Key Design Challenge

Clinical supervision hierarchies, HIPAA-adjacent data handling, and client-to-clinician assignment scoping

New User Types

Caregiver, Parent, Family Member with invited read-only access

Expansion Context

Private home tracking of diet, medication, and behavior with selective sharing to teachers, clinicians, and doctors

Key Design Challenge

Private data that is never visible to the school org by default, with explicit one-time share links and revocation controls

New User Types

Individual consumer users with no org affiliation

Expansion Context

Personal behavior and mood tracking with trend visualization, goal setting, and PDF export for therapist sharing

Key Design Challenge

Consumer-grade simplicity over institutional complexity, with a quick-tap logging experience and streak-based engagement

Reflections

What This Project Taught Me

Permission design is UX design

The most important design decisions in EduTrend were not visual. They were about what each role should and should not be able to see. Getting that architecture right first meant every screen that followed had a clear, defensible logic behind it.

Speed is a safety feature in high-stakes environments

A paraprofessional who cannot log a behavior incident quickly enough will stop logging. That data gap has real consequences for a student. Designing for speed in the logging flow was not a convenience feature. It was a safety feature.

Systems thinking at the start saves everything later

Building the design system before the screens meant every component decision was made once, intentionally, and then reused everywhere. It accelerated the engineering build and made the product feel cohesive in a way that ad-hoc design never could have.

Onboarding is where trust is first built or broken

A school administrator signing their institution up for a platform that will hold sensitive student data is making a trust decision before they see a single feature. The onboarding flow had to earn that trust through clarity, security signals, and institutional formality done simply.
